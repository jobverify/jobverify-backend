# Referral outreach

Outreach extends the existing API and MongoDB deployment. It is available to authenticated accounts independently of paid-plan access. `Application.status` continues to mean an employer page was opened or the user manually confirmed an application. Contacting a person does not change that status.

## Entry points and requests

The job-detail page has **Find referrals**, below Apply; saved-job cards offer the same explicit action. A signed-in click starts a job-scoped discovery request. Viewing job pages, saved jobs, or application history never starts discovery, provider lookups, or model inference. Reopening an existing result is free of provider requests until the user explicitly requests refresh.

New route groups are `/api/user/outreach`, `/api/user/gmail`, and `/api/user/campaigns`. They use the existing authentication, JSON mutation, CSRF, and no-store behavior. Private task IDs and thread IDs are checked against the current account. Discovery may complete from a shared public-evidence cache; profiles, drafts, selected contacts, campaigns, and task inputs stay private.

## Configure discovery

Discovery defaults to `OUTREACH_DISCOVERY_PROVIDER=actions`. An explicit click saves a MongoDB task and dispatches `outreach-discoveries.yml`. The runner starts a private SearXNG container and the pinned local LFM/llama.cpp model, saves the result to MongoDB, then stops both services. There is no permanent model endpoint, inference API key, or Tavily requirement for this provider.

Configure `GITHUB_PAT` and `GITHUB_REPO` on the backend. The GitHub token needs repository access to read and dispatch Actions workflows. Deploy the discovery workflow to that repository's default branch. Set its `MONGO_URI` Actions secret; optionally set `HUNTER_API_KEY` as an Actions secret for work-email enrichment. Never place these secrets in frontend configuration or Actions variables. MongoDB must be reachable from both the backend and the GitHub-hosted runner; connection failures need to be resolved before a live queue test.

Before enabling dispatch, block paid Actions usage in repository/organization billing and verify remaining free eligibility/allowance. Set `OUTREACH_ACTIONS_ENABLED=true` and `OUTREACH_ACTIONS_FREE_CONFIRMED=true` in **both** the backend environment and the repository's Actions variables. They default to disabled. These flags record the operator's confirmation; they cannot enforce account-level GitHub billing settings. Discovery and drafting have **no application monthly workflow cap**. The shared monthly run counter remains for operational visibility and never rejects dispatch. Legacy `OUTREACH_ACTIONS_MONTHLY_RUN_LIMIT` values are ignored, so old Render settings and existing counters need no reset or migration. Five fresh discoveries and ten draft requests per user per UTC day still apply. Cache hits need no Actions access, dispatch, or daily allowance.

SearXNG uses a digest-pinned official image with Brave, DuckDuckGo, and Bing enabled. The application caps fresh SearXNG searches at 1,000 per UTC month across all users; this is a local workload limit, not a paid search subscription. Public search engines can throttle or block GitHub-hosted IP addresses, and indexed results can be incomplete. A controlled live test is still needed to assess availability and contact relevance. Upstream failures remain failed tasks with explicit retry rather than successful empty results. There is no paid fallback or dependency on a public SearXNG instance.

`HUNTER_API_KEY` is optional: useful contacts survive missing email results, outages, and exhausted credits. Use Hunter's free plan with automatic top-ups and paid purchases disabled. Fifty monthly Hunter reservations are shared across the application. Reservations are persisted before calls, including failed or ambiguous calls. For legacy Tavily discovery only, explicitly set `OUTREACH_DISCOVERY_PROVIDER=tavily` and `TAVILY_API_KEY` on the backend; it retains its separate shared 1,000-credit monthly allowance and needs no discovery Actions run.

Discovery searches public indexed referral and hiring evidence for an existing stored job. It ranks explicit referral-post authors first, hiring-post authors second, relevant employees and team leaders third, and recruiters last, with at most three results. People require a named source and employer evidence; ordinary employees are labeled potential referral contacts, without claiming willingness or ability to refer. Former employees are excluded. Results include the evidence URL and excerpt. Email lookup uses the employer domain, not the ATS hostname. Only a provider verification result produces the verified label. Missing enrichment leaves the contact available with its original source. Users can enter an address, then explicitly confirm it before sending.

The model selects at most three indices from a bounded pool of source-backed contacts. It cannot supply names, relationships, addresses, URLs, or verification labels. Invalid or incomplete model output fails the task. Successful discovery caches live for seven days and are keyed by job context, provider, and discovery policy; switching providers or changing job facts invalidates reuse. Email evidence is reusable for 30 days. Neither cache is proactively refreshed.

The discovery workflow uses one concurrency group, a standard Ubuntu runner, a ten-minute job limit, an eight-minute worker-step limit, and at most three tasks per batch. Its internal deadline leaves at least thirty seconds for cleanup before the step ends; model downloads, hashing, extraction, and health checks respect the shared deadline. Empty queues skip service startup. Expired leases are recovered only for persisted user requests. Startup failures preserve context and release unchanged pending requests for explicit retry. Model files are the only Actions cache; search configuration and responses are not cached. Candidate profiles and private messages never enter this discovery workflow. Logs contain only counts and bounded error categories, with no prompts, contact evidence, provider responses, or credentials; Docker container logging is explicitly disabled.

Publication uses atomic task and cache ownership/expiry checks. A lost task lease cannot publish either a private result or a shared refresh. Completed public evidence is shared independently of the requesting account and can remain for seven days after that account is deleted; private task/profile/message records are removed and never recreated by the worker. An incomplete engine response with no grounded contacts is a retryable failure, while useful sourced contacts from healthy engines can still be returned.

## GitHub Actions drafting

The model runs on demand inside GitHub Actions. The app queues a draft in MongoDB, dispatches `outreach-drafts.yml`, and polls its private task API for the saved result. There is no permanent public model server or model API key; the backend uses its GitHub token to dispatch work.

To check model hosting independently, open **Actions → Jobverify Model Smoke Test → Run workflow** (`outreach-model-test.yml`). This downloads/verifies the pinned model and runtime, generates and validates one synthetic draft, prints only counts, then stops the runtime. It needs the two enabled Actions variables but no MongoDB, Tavily, Hunter, or inference-provider keys. It uses the same runner and time limits as normal generation. A separate workflow keeps synthetic tests from being mistaken for an active queue worker. A successful smoke test proves model startup and structured generation; it does not prove MongoDB connectivity, contact search, or draft quality for real users.

The existing `GITHUB_PAT`, `GITHUB_REPO`, and Actions `MONGO_URI` secret support an isolated outreach drafting workflow. It is separate from the scraper, description rewrite, and classification stages. Enable both `OUTREACH_ACTIONS_ENABLED` and `OUTREACH_ACTIONS_FREE_CONFIRMED` after deploying the workflow and setting repository/organization billing to block paid Actions usage. Run counts are recorded without an application monthly ceiling; GitHub's own eligibility, capacity, and billing controls still apply. Standard GitHub-hosted runners in public repositories have free compute usage; private-repository allowances are measured in minutes, not a fixed run count. See [GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

Set those same two enable/free-confirmation flags to `true` in the backend environment **and** in the backend GitHub repository's Actions variables. The workflow has its own guard; setting only backend flags leaves the Actions job disabled. Keep `MONGO_URI` in Actions secrets, not Actions variables.

Standard Ubuntu runners load the pinned LiquidAI LFM2.5-1.2B-Instruct Q4_K_M model with a pinned llama.cpp runtime. Only the immutable model file is cached; the runtime is downloaded separately and checked against its pinned checksum. Candidate biographies, prompts, and generated messages must not be logged, cached, uploaded as artifacts, or included in workflow input names. The workflow receives opaque work identifiers, reads requested tasks from MongoDB, and writes results back there.

Drafting is asynchronous and has a ten-request daily account limit. The UI shows queued/running/completed/failed states and supports leaving and returning. Batches are bounded, generation is serial, and workflows time out after ten minutes. Account existence and thread revision are rechecked before publishing a result so deletion or manual edits cannot be undone by a late model response. Drafts remain suggestions that the user reviews and edits.

## Gmail authorization and campaigns

Concurrent drafting requests in one backend process share a workflow dispatch and one usage increment. Worker startup failures release unchanged queued tasks for explicit retry. The Actions process exits with failure when a batch contains failed drafts; saved text and another worker's active leases are preserved.

Create a Google OAuth web client and enable the Gmail API. Set the exact callback URL in Google Cloud and `GMAIL_REDIRECT_URI`; provide `GMAIL_CLIENT_ID` and `GMAIL_CLIENT_SECRET`. Google login remains an identity-only flow. Connecting Gmail separately requests sending permission and sender identity, with state, session binding, and PKCE. Public distribution of the sensitive `gmail.send` scope needs Google's applicable OAuth verification.

Set `GMAIL_TOKEN_ENCRYPTION_KEY` to the base64 encoding of exactly 32 cryptographically random bytes. Refresh tokens are encrypted with AES-256-GCM before storage. Store this key outside the database, back it up securely, and keep it stable across restarts. A different key cannot decrypt existing connections; disconnect and reconnect affected accounts when rotating it.

Campaigns start as editable draft groups. Users choose recipients, review the sending account, edit text, remove items, and explicitly press Send. Approval freezes the item snapshots. The server sender processes only approved queued items, with atomic claims, a shared three-minute gap for each sender account, and 25 messages per rolling 24 hours per user. Cancel stops unsent items; it cannot recall an accepted or in-flight email. An ambiguous provider timeout is shown for manual review and is never automatically resent.

Campaign edits and approval require the `revision` of the campaign that was reviewed. A stale version is rejected rather than sending another tab's unreviewed changes. Draft campaigns are bound to the reviewed sender and connection version; reconnecting Gmail invalidates affected drafts and approvals. At most one Jobverify account may have an active connection to the same normalized Gmail address. Disconnect it from the original account before transferring it. Removing a tracked outreach contact cancels its pending campaign items; completed and in-flight send history is retained.

Disconnecting Gmail revokes authorization and stops unsent work. Account deletion removes its private outreach data and prevents background results from recreating it. Replies and interviews are manual tracker updates; send-only permission provides no inbox monitoring. Follow-up reminders default to four weekdays after sending. Follow-up sending still requires a new reviewed approval.

## Deployment and validation

1. Deploy backend models, routes, worker lifecycle, and the separate discovery/drafting workflows with Actions dispatch disabled initially. Workflow files must be on the configured repository's default branch before dispatch.
2. Register new indexes through the existing `db:indexes:plan` / `db:indexes:apply` process and its mutation safeguards. No rewrite of existing application records is required.
3. Configure MongoDB connectivity, GitHub repository access, free-usage controls, optional Hunter enrichment, and Gmail OAuth secrets. Default referral discovery needs no Tavily key. The frontend needs no new provider secrets.
4. Run the synthetic model smoke workflow, then enable discovery/drafting for a controlled queue test after checking billing controls. Validate SearXNG availability and database access from the runner before frontend activation.
5. Run the outreach API/provider/queue tests and desktop/mobile Playwright coverage using fixtures. Use a disposable local MongoDB for database integration tests. Automated tests must never send real outreach or invoke production workflows.

Operational records should retain task status, result counts, bounded error categories, provider-credit consumption, workflow identity, and send status/timing. Avoid logging message contents, candidate text, tokens, or complete provider responses.

Initial scope does not include CV uploads, standalone external-job searches, automated reply detection, open-tracking pixels, or automatic follow-up sequences.
