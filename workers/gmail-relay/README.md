# Private Gmail relay

Render calls this Worker over authenticated HTTPS. The Worker submits one fixed
password-reset email to Gmail over TLS on port 465. The backend still issues,
stores, validates and expires reset tokens. No mailbox-provider API is required.

Deployed relay: `https://jobverify-gmail-relay.jobverify-gmail-relay.workers.dev`.
Gmail authentication from this deployed Worker was verified on November 6, 2026,
without sending an email. Backend activation and a real delivery test are
separate steps below.

Only password-reset delivery uses the relay. Registration verification and
email-change verification retain their existing SMTP transport.

## Install and authenticate

Use Node 24.14 or later in the 24.x line. From this directory:

```powershell
npm ci
npx wrangler login
```

Complete Cloudflare login in your browser. This authorizes Wrangler, not the
website frontend. The package lock generated by installation should accompany
deployment changes.

## Prepare configuration and secrets

`wrangler.jsonc` allows reset links only for `https://www.jobverify.in`, as
confirmed by the site owner. Change it only if the frontend origin changes.
Select two unused `namespace_id` values if 1001/1002 are already used by another
rate limiter in your Cloudflare account.

The existing backend `.env` already contains Gmail `SMTP_USER` and `SMTP_PASS`.
From the backend root, run:

```powershell
node scripts/prepareGmailRelay.js
```

This writes an ignored `workers/gmail-relay/.dev.vars` with `GMAIL_USER`,
`GMAIL_APP_PASSWORD`, and a new random `RELAY_SECRET`. It preserves the relay
secret when rerun. Treat `.dev.vars` as credentials; do not commit or share it.
Gmail requires an app password with 2-Step Verification enabled.

From this directory, run:

```powershell
npm test
npm run build
npm run deploy
npx wrangler secret bulk .dev.vars
```

If prompted for a Cloudflare account, choose the intended account. No DNS or
paid Email Service setup is needed: use the `workers.dev` URL that deployment
prints. Until all secrets are uploaded, the Worker refuses delivery.

## Verify Gmail from Cloudflare without sending an email

From the backend root, using the deployed Worker origin:

```powershell
node scripts/verifyGmailRelay.js https://jobverify-gmail-relay.YOUR-SUBDOMAIN.workers.dev
```

This calls the authenticated `/verify-smtp` endpoint with the local relay secret.
It checks Gmail connectivity and authentication but does not send an email.
Node/SMTP tests and a successful bundle alone do not prove Cloudflare-to-Gmail
delivery. Google can reject sign-in from a new hosting location; investigate
Google account security activity if the deployed check returns `EAUTH`.

## Activate on Render

Deploy the backend changes, then add these **backend** environment variables:

```dotenv
EMAIL_RELAY_URL=https://jobverify-gmail-relay.YOUR-SUBDOMAIN.workers.dev
EMAIL_RELAY_SECRET=<RELAY_SECRET from the ignored .dev.vars file>
```

Use the Worker origin with no path. Set backend `FRONTEND_ORIGIN` to
`https://www.jobverify.in` so it generates links matching the Worker allowlist.
Save and redeploy/restart the backend for environment changes to take effect.
Never add any relay or Gmail secret to Vercel/frontend environment variables.

After SMTP verification passes, request one real password-reset email from the
live profile and verify the link works. Keep the Gmail account's sending limits
in mind; Workers does not remove Gmail's quotas.

To roll back, remove `EMAIL_RELAY_URL` and restart the backend. This restores the
existing direct SMTP path, which still requires SMTP access from the host.

## Contract and protections

- `POST /send-password-reset`: JSON `{ "to": "user@gmail.com", "resetLink": "https://www.jobverify.in/reset-password#token=<64 hex characters>" }`.
- `POST /verify-smtp`: no mail payload and no email sent.
- Both require `Authorization: Bearer <RELAY_SECRET>` (at least 32 characters).
- One plain recipient address; maximum body 2048 bytes. No arbitrary HTML,
  sender, headers, attachments or SMTP destination accepted.
- Exact HTTPS frontend origin, `/reset-password`, no credentials/query parameters,
  and a single 64-character hexadecimal token in the fragment.
- Gmail TLS/certificate validation remains enabled. Success means Gmail accepted
  the message, not guaranteed arrival in the inbox.
- `gmailSocket.js` opens verified TLS directly by hostname, then supplies the
  secured connection to Nodemailer. This avoids the DNS/address-family setup
  that failed in the deployed Workers runtime. The hostname, port, SNI and
  certificate validation settings are fixed in code.
- Rate limits: 20 authenticated operations/minute overall and one email per
  recipient/minute, approximately **per Cloudflare location**, not a global
  Gmail quota. Existing backend authentication and reset rate limits still apply.
- Provider errors are logged only as safe error codes. No credentials, recipients,
  email bodies or reset links are logged by this code.
- No automatic retries or SMTP fallback when the relay is configured. Relay
  failures use the backend's existing reset-token cleanup and retryable error.

The Worker URL is internet reachable; its secret authenticates server callers.
It is not a private-network endpoint. Rotate both copies of `RELAY_SECRET` if it
is exposed. Cloudflare's Workers request/CPU limits and Gmail quotas still apply;
check deployed metrics before relying on a free tier for production volume.
